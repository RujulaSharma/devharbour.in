Build a hackathon submission a reviewer can reproduce

Choose a narrow scope, show evidence, disclose limitations, and prepare a reliable demonstration.

A hackathon submission is an argument supported by a working artifact. A feature list says what you hoped to build; a reproducible demonstration shows what actually works. This guide uses a campus lost-and-found application as an example, but the same process works for other student projects.

Choose one complete user journey

Write a sentence that names a user, a task, and a measurable result: “A student can post a found item and another student can filter by location.” Finish that path before adding chat, recommendations, or a dashboard. Define what counts as done: a valid post persists, appears after refresh, and is visible to another visitor.

Allocate the work around dependencies

Start with a simple data model and a tiny end-to-end implementation. One teammate can build the post form while another implements the API contract. Agree on field names and an example response before working independently. Reserve the last portion of your available time for integration, accessibility, deployment, and a recorded backup demo.

Write a README that removes guesswork

  • Problem: who experiences it and what you observed. Label assumptions as assumptions.
  • Solution: the single journey your prototype supports.
  • Run: dependency installation, variable names, start command, and demo URL.
  • Evidence: screenshots or a short video showing real inputs and results.
  • Limits: incomplete features, sample data, paid API dependencies, and known errors.
  • Credits: teammate contributions, libraries, datasets, and licenses.

Make the demo resilient

Begin from a clean browser session. Explain the problem, perform the core task, then show the resulting stored record. Keep a short recording in case a network dependency fails. Do not present prerecorded output as live behavior. If an AI feature uses fixed examples, disclose that instead of implying broad reliability.

Protect people and other creators

Use invented contact information in demo data. Remove access tokens, private participant lists, and account passwords from repositories and screenshots. Check the licenses of images, music, models, and datasets; attribution alone does not grant permission to reuse a work. Give reviewers a safe demo account only when event rules allow it.

Final submission check

  1. Confirm the event's official deadline, eligibility, team rules, and required files.
  2. Verify the repository and demo are accessible to reviewers.
  3. Test all links while signed out of your developer accounts.
  4. Check that the video matches the submitted commit.
  5. Record the submission confirmation and the version you submitted.

Dev Harbour's hackathon listings link to event pages; the organiser's published rules control participation and awards. A participation certificate is not an academic qualification or a promise of employment.
